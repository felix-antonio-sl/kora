## Decisiones
- El CLI clínico HSC debe diseñarse como interfaz común para agentes y operador humano: patrón de uso `agente ↔ CLI ↔ Félix`.
- El eje dominante no será un contexto único (urgencia u hospitalización), sino la reconstrucción y operación sobre la historia clínica longitudinal del caso, pudiendo entrar y salir de urgencia, hospitalización, ambulatorio, comité y domicilio sin perder coherencia.
- La gramática debe soportar dos modos a la vez: comandos atómicos autosuficientes y trabajo contextual por paciente/sesión.
- La v1 debe incluir lectura y escritura segura desde el inicio.
- Se acepta que un dato atómico pueda devolverse como lista corta, siempre que pertenezca a una sola familia semántica.

## Requisitos funcionales aclarados por el operador
- Necesita consultas y escrituras rápidas, con capacidad de conectar, reconectar, limpiar sesión/cookies y volver a entrar limpio.

## Implicancias de diseño
- El núcleo ya no puede ser solo un set de teclas de lectura; debe separar explícitamente una gramática de consulta atómica y una gramática de actos clínicos/registrales asistidos.
- FHIR sigue siendo el vocabulario común para nombrar recursos y diferenciar dato atómico, resumen y dato derivado, pero la ergonomía clínica manda sobre pureza técnica.
- Habrá que distinguir tres estratos: `atomos`, `macros clínicas de trabajo` y `escritura segura`.

## Contratos y decisiones de fase
- Se cerró `HODOM HSC v0` como primer caso real de validación para OPModel bajo baseline stabilization.
- Regla operativa asociada: usar HODOM HSC para validar modelamiento del sistema real, no para abrir producto nuevo (sin FHIR/SNOMED/software HODOM OS en esta fase).
- Estructura mínima aprobada para HODOM HSC v0: entidades del servicio HODOM HSC, 13 subprocesos canónicos, requirements/assertions normativas y operativas mínimas, y un conjunto explícito de exclusiones fuera de scope.
- Se reafirmó la disciplina de baseline stabilization para OPModel: estabilizar antes de expandir, y usar casos reales solo dentro de recortes controlados.

## Hallazgos observables
- Test de consumibilidad de `cli-hsc` como usuario/agente: el entrypoint Python heredado está roto por shebang apuntando a otra ruta; `--help` también falla por import temprano de dependencias (`bs4`) antes de entregar ayuda básica. Conclusión durable: la superficie mínima consumible aún no está cerrada.
- Para consumo agente de `cli-hsc`, el gate mínimo quedó definido como: `help`, `status`, `login`, `who <rut>` y `sv <rut>` funcionando con salida estable y errores legibles.

## HODOM HSC — Diseño del sistema operativo
- Se absorbió corpus completo: ERD 43 tablas, FHIR R4 37 recursos, OPM v2.5 (SD–SD1.6+), Modelo Categorial v4.1 (6 categorías), Manual REM 2026, documentación legacy, formularios reales HSC.
- Se identificaron 17 usuarios del sistema, agrupados en: clínicos directos (6), coordinación/gestión (3), red/derivación (3), reporte/supervisión (3), no profesionales (2).
- Se derivaron 11 módulos funcionales naturales del sistema.
- Entregable producido: `output/2026-04-07-usuarios-sistema-hodom-hsc.md`
- Siguiente paso definido: historias de usuario núcleo por módulo.

## Portafolio / prioridades
- Lectura de portafolio en `/home/felix/projects`: `openclaw` es el producto principal más maduro; `pca` aparece pequeño pero sano; `hdos` funciona como demo/prototipo válido; `opmodel` tiene alto valor real pero baseline aún no cerrada; `hsc-cli` es estratégico pero todavía frágil en consumibilidad.
- Recomendación durable de gestión: proteger/escalar `openclaw` y `pca`; estabilizar antes de expandir `opmodel` y `hsc-cli`; mantener `hdos` como demo controlado; exigir prueba de valor o podar `kora-panel` y `opcloud-reports`; tratar `docker-stacks` como soporte operacional, no como producto.

## Coordinación y reporting
- Se consolidó una regla de comunicación con el operador: reportes breves, claros y accionables cuando haya contratos, evals o decisiones de fase con valor real, evitando teatro y duplicación vacía.
- El operador pidió más visibilidad directa y menos coordinación opaca sólo con Clawforge; queda como patrón estable trabajar más a la vista del operador y mantener actualizaciones regulares con foco en `qué quedó listo / qué sigue / qué riesgo veo`.
