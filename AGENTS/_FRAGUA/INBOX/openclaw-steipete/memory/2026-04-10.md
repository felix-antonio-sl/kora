# 2026-04-10

- `opmodel` entered a deliberate deep structural refactor of the web visual layer. Decision: do not do a total rewrite; instead do a staged architectural reshape around a canonical `EffectiveVisualSlice(opdId)` boundary.
- Created repo docs to anchor the refactor direction:
  - `docs/opl-first/11-effective-visual-slice-adr.md`
  - `docs/opl-first/12-web-visual-refactor-plan.md`
- Core architectural conclusions to preserve:
  - the real visual pipeline is `projection -> effective visual slice -> layout -> routing/overlays -> report/lint -> canvas`
  - canvas should be a consumer, not a semantic authority
  - `internal` is strong visual semantics, not incidental appearance metadata
  - `finalizeLayout()` is overloaded and should be split into merge/apply/normalize/relax/diff stages
  - relaxation must be policy-by-strategy, not universal
  - structural clustering should be centered on parent, not `type::parent`
  - object in-zoom needs its own visual policy distinct from process in-zoom
- Phase 1 implementation started in code:
  - `projection-view` now exposes an explicit `EffectiveVisualSlice`
  - `visual-report` was moved to consume that canonical effective slice
  - store/UI began migrating from `projectionSlice` language toward `visualSlice`
  - canvas projection tests were updated accordingly
- Validation snapshot after Phase 1 slice work:
  - web build OK
  - `88/88` test files passing
  - stress visual report back in healthy range around `SD=78`, `SD1=82`
- Important human-quality finding to remember: even with the pipeline healthier, visual audit/report still produced findings with `undefined` messages for categories like `label-cluster`, `degenerate-bounds`, `crowded-diagram`. That signals the audit layer still under-expresses real perceptual problems and should be cleaned up before trusting score/report semantics too much.
- Fugaz provided useful distilled architecture insights that aligned with the chosen direction, especially: canonize one effective visual slice, treat patches as deterministic composition instead of first-match lookup, preserve `internal`, make relax strategy-specific, and keep canvas thin.
- Deep refactor was completed in its main architectural contract with these additional commits:
  - `40320b6` Split finalizeLayout into merge apply diff steps
  - `41a7137` Make layout relaxation policy strategy-driven
  - `b8138d3` Split object and process in-zoom layout strategies
  - `bf51a3c` Make OpdCanvas consume effective visual slice
- After those commits, `opmodel` passed loop closure again with `bun run test` (`88` test files / `1223` tests) and `bun run web:build`.
- A second local line that initially looked like unrelated dirty work was later validated and integrated. Durable outcome:
  - `edge-router.ts`, `visual-lint.ts`, `capture-visual-audit.ts`, `fan-overlay.ts`, related tests/fixtures/scripts were coherent and worth keeping
  - `artifacts/visual-audit/` should be ignored as generated output, not tracked
  - integrated as commit `ef0bb28` `Add visual audit fixtures and fan overlay tooling`
- Strong caution for future sessions: the deep refactor is architecturally complete, but not visually validated against giant imported OPL benchmarks. A real regression surfaced on `hdos-app/docs/opm-hodom-completo-opl-import.txt` after Docker redeploy and manual inspection: SD/SD1 became dramatically worse, with huge fan-out/cross-container link explosion and rightward graph collapse.
- Preserve this diagnosis: the HODOM OPL import is a canonic stress benchmark exposing unresolved weaknesses in imports with very high density and many shared externals. The likely gaps are not basic rendering bugs but missing high-level layout policies for massive process in-zoom diagrams, especially external packing, shared-object clustering, long-link suppression/reduction, and stronger heuristics for large OPL-derived models.
